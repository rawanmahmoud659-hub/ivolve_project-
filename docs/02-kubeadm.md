# 2. Kubernetes Cluster with kubeadm

The Kubernetes lab used Ubuntu nodes, containerd as the runtime, and Flannel as the CNI. Run the node preparation steps on **every** control-plane and worker node. The commands below document the lab sequence; choose a Kubernetes package version supported by your OS and keep kubeadm, kubelet, and kubectl compatible across nodes.

## Prepare every node

```bash
sudo swapoff -a
sudo modprobe overlay
sudo modprobe br_netfilter
sudo modprobe vxlan
cat <<'EOF' | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
vxlan
EOF
cat <<'EOF' | sudo tee /etc/sysctl.d/k8s.conf
net.ipv4.ip_forward = 1
net.bridge.bridge-nf-call-iptables = 1
EOF
sudo sysctl --system
sudo apt-get update
sudo apt-get install -y containerd runc containernetworking-plugins
sudo mkdir -p /etc/containerd
containerd config default | sudo tee /etc/containerd/config.toml >/dev/null
sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
sudo systemctl enable --now containerd
```

Disable swap persistently in `/etc/fstab`. For an Ubuntu cluster on Kubernetes 1.35, install the three tools from the versioned package repository:

```bash
sudo apt-get install -y ca-certificates curl gpg
sudo mkdir -p -m 755 /etc/apt/keyrings
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.35/deb/Release.key \
  | sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.35/deb/ /' \
  | sudo tee /etc/apt/sources.list.d/kubernetes.list
sudo apt-get update
sudo apt-get install -y kubelet kubeadm kubectl
sudo apt-mark hold kubelet kubeadm kubectl
kubeadm version
kubelet --version
kubectl version --client
```

These package steps follow the [official Kubernetes v1.35 kubeadm installation guide](https://v1-35.docs.kubernetes.io/docs/setup/production-environment/tools/kubeadm/install-kubeadm/). For a different minor version, use the matching versioned repository and guide.

## Initialize the control plane

```bash
sudo kubeadm init --pod-network-cidr=10.244.0.0/16 \
  --cri-socket=unix:///run/containerd/containerd.sock
mkdir -p "$HOME/.kube"
sudo cp /etc/kubernetes/admin.conf "$HOME/.kube/config"
sudo chown "$(id -u):$(id -g)" "$HOME/.kube/config"
kubectl cluster-info
```

The pod CIDR matches the Flannel configuration from the lab. Keep `admin.conf` private.

## Install Flannel and join workers

```bash
kubectl apply -f https://github.com/flannel-io/flannel/releases/latest/download/kube-flannel.yml
kubectl -n kube-flannel rollout status daemonset/kube-flannel-ds --timeout=180s
kubeadm token create --print-join-command
```

Run the generated join command on each worker, adding `--cri-socket=unix:///run/containerd/containerd.sock` if needed. Use the real token and CA hash generated by kubeadm; do not commit them.

## Verify

```bash
kubectl get nodes -o wide
kubectl get pods -A
kubectl -n kube-system get pods
kubectl -n kube-flannel get ds,pods
```

On 12 November 2026, the inspected cluster showed control plane `ip-172-31-7-13` and workers `ip-172-31-4-135` and `ip-172-31-13-135`, all `Ready`. This is observed lab state, not a promise that a fresh cluster will use the same node names or versions.
